\section{System Context, Architecture, and Interfaces \applicability{Development, Hybrid, Game; Research Software Prototype}}
The system boundary contains the Flutter web/Android client, the ASP.NET Core
marketplace API, the PostgreSQL/PostGIS database, Redis, SignalR, and the
asynchronous Python/FastAPI AI service. Customers use the client for lot
discovery, communication, negotiation, and reservation. Admins manage users,
categories, thresholds, flagged listings, and AI overrides. AWS S3 stores listing
photographs. The AI service returns classification, defect, condition,
consistency, and price signals to the decision engine.

\section{Research Methodology and Experimental Design \applicability{Research, Hybrid}}
\subsection{Study or Experimental Design}
The project will evaluate the integrated system using held-out image data and
Admin review decisions. Each submitted lot passes through the same classification,
defect, condition, consistency, and price stages. Results are compared with
validated labels, sourced reference prices, and human review outcomes.

\subsection{Population, Sample, Participants, or Dataset}
The AI pipeline will use existing public building-defect datasets, including
YOLO-format datasets, SDNET2018, and MBDD2025, supplemented by a small
team-collected validation set of marketplace-style phone photographs. New-material
prices will be collected from published Pakistani construction-pricing sources.
Surplus depreciation will be informed by structured interviews with 5--10 Lahore
dealers and contractors. User requirements will be validated through interviews
with 4--6 contractors/suppliers and a brief questionnaire.

\subsection{Analysis and Evaluation Protocol}
Evaluation will report material-classification accuracy and confusion patterns,
defect-detection precision and recall per defect class, agreement between the
automated publish/flag decision and Admin review decisions, and price-estimate
MAE/RMSE against sourced reference prices. The real-photo validation set will be
kept separate from training data.

The API accepts the lot and replies at once with status Screening, and the lot's
status in PostgreSQL acts as the queue. A background worker takes one lot at a time.
It creates the pre-signed URLs just before each call, calls the AI Service over
HTTPS, and receives the results in that response, so the AI Service stays stateless
and stores nothing. The AI Service downloads the photos directly from AWS S3. Partial
results count as a failed attempt, so no lot is auto-published without all checks.
After a failed attempt the worker waits a few seconds, with jitter, and retries once;
a 4xx error is not retried. The Decision Engine chooses Auto-Publish or Send to Review,
and every Mixed-condition lot goes to review. The worker saves the results, the
decision, and the status in one database transaction. If the retry fails, the lot
receives the grade Not Assessed with no price suggestion and moves to Pending Review.
After a restart, the worker resumes any lots still in Screening.

The API works inside one transaction and reads the lot's status and version first.
A lot that is already Reserved or Expired is refused at once. For a Published lot,
the update succeeds only if the version is unchanged since it was read, so when two
buyers reserve at the same moment the second receives a version conflict. A lot can
therefore never hold two Active reservations.

checks that the sender belongs to the thread and persists the message before
delivery, so no message depends on the recipient being connected. An online seller
receives the message immediately. An offline seller receives it on reconnecting,
when the hub reads the undelivered messages from PostgreSQL. When the seller reads
the message, the hub saves the read status and tells the buyer.

The system runs on two AWS machines. The application server hosts the API, the
SignalR hub, PostgreSQL with PostGIS, and Redis, and the AI Service node hosts
Python, FastAPI, and the model files. AWS S3 and the LLM provider are external
services. The AI Service reaches AWS S3 directly, using the time-limited, read-only
pre-signed URLs it receives from the API, and stays in the same AWS region as S3
(DD-20).

In the deployed system, CLIP, YOLO, and XGBoost all run on CPU on the AI Service
node. A cloud GPU would cost about \$384 a month, far beyond the project budget, and
because screening runs in the background, a few seconds per lot is acceptable.
Training, fine-tuning, and large test runs use a GPU on Google Colab, as the proposal
budgets. Colab is not part of the deployed system, so it does not appear in
Figure~\ref{fig:deployment-diagram}.

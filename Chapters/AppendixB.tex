\section{REST API Contract}
\label{sec:rest-api}
All endpoints live under \texttt{/api/v1/} and use HTTPS only. Requests and responses are
JSON with camelCase field names, and status, grade, and flag values are spelled exactly as
locked. Every request except sign-up, sign-in, and password reset carries a bearer access
token; the server checks the role and, for owner-only actions, that the user owns the
resource (SEC-01). Lists are paged with \texttt{page} and \texttt{pageSize}. Every error
uses one format, Problem Details for HTTP APIs~\citep{rfc9457}: \texttt{type},
\texttt{title}, \texttt{status}, \texttt{detail}, and a project \texttt{code} such as
\texttt{LOT\_ALREADY\_RESERVED}. Common errors are not repeated per row: 401 (no or expired
token), 403 (wrong role), 404 (not found or not visible), 429 (rate limit), and 500.
The last column maps each endpoint to the sequence-diagram message it implements.

\section{AI Service Interface}
\label{sec:ai-service-interface}
The ASP.NET Core backend calls the AI Service over INT-02 using HTTPS, as shown in
Figure~\ref{fig:sd-01} and Figure~\ref{fig:sd-05}. The AI Service requires a secret
API key and accepts traffic only from the API server (SEC-22). It stays stateless,
stores nothing, and returns signals only; the Decision Engine in the API makes the
publish or review decision. Routes, timeouts, retries, and link expiry are
provisional. JSON field names use camelCase, and status, grade, and flag values are
spelled exactly as in the rest of this document.

Purpose & Classify the material, detect visible defects, grade the condition, check description--image consistency, and estimate a surplus price for one lot (FR-02, FR-03). \\
Caller & Background worker in the ASP.NET Core backend. The lot's status in PostgreSQL acts as the queue, and the worker takes one lot at a time. It starts only once GET /health confirms the models are loaded, and after a restart it resumes any lots still in Screening. \\

Response fields & \texttt{material} and \texttt{materialConfidence} (0--1); \texttt{photos}, one entry per photo with its \texttt{material}, \texttt{confidence}, \texttt{quality} (ok, blurry, or dark), \texttt{defects} (each with \texttt{class}, \texttt{confidence}, and a normalised \texttt{box}), and \texttt{grade}; \texttt{grade} for the lot (Good, Minor, Major, Mixed, or Not Assessed); \texttt{consistency} (\texttt{materialMatch}, \texttt{conditionClaim}, \texttt{conditionConflict}); \texttt{priceEstimate} (\texttt{low}, \texttt{mid}, and \texttt{high} per unit, in PKR); \texttt{modelVersions}; \texttt{processingMs}. The response carries signals only: the Decision Engine in the API derives the flag reasons from them using the Admin's thresholds (DD-24). \\
Result return & In the HTTPS response, with no callback or polling. The worker saves the results, the decision, and the status in one database transaction. \\
Timeout & 120 seconds. \\
Retries & One, from the worker only, after a wait of a few seconds with jitter. Saving results is safe to repeat for the same lot. \\
Error behaviour & Partial results count as a failed attempt, so no lot is auto-published without all checks. A 4xx error is not retried; the lot goes to Pending Review with the flag reason AI Unavailable, and the error code is logged. \\
Fallback & If the retry fails, the lot receives the grade Not Assessed with no price suggestion and the flag reason AI Unavailable, and moves to Pending Review (FR-28). The API sets this flag itself, so it is not an AI Service response value. \\
